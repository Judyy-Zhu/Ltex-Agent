# Pi-agent 重建《几何原本》的 Lean / Litex 对比实验

本实验比较同一个模型在同一 Pi-agent 框架下，使用 Lean 或 Litex，根据同一原典构建正确数学库的完成率与资源消耗。最终范围为 13 卷、465 个编号命题；另外记录 140 个基础条目和 39 个显式推论、引理。采用现有 `tasks/` 源文清单，不继承历史证明成绩。

实际交给 agent 的材料、共同提示词、两种语言的角色卡、I.1 配对输入和 token 计数辅助代码见 [agent 输入包](agent-kit/README.md)。共同数学任务与语言适配分开；计量与裁判文件由控制器持有，不交给 agent 修改。

当前已实现 [全书批量入口与运行说明](RUN_FULL.md)，覆盖 644 项、每次重复 1288 个串行交错 agent 任务。两边各自保留机器候选库，失败增量不发布；中断恢复不免费重跑，原始时间和 token 保留。准确率需要另行导入绑定源文件的语义审核。当前全书可做探索运行，尚不宣称正式数学基础已经全面认证。

已实现 [新运行器](runtime/README.md)。开发 v5 在 v4 的持久会话上接入 [最小平面种子](seeds/README.md)，使用固定检出的 Pi、持续的工具服务、Litex 原生 Session 与 Lean 原生 REPL；独立最终文件检查保持另开进程。原生失败恢复、重放、修改失效以及真实 Pi 工具连接已用离线控制测试。早期 v1/v2 的 I.1 冷文件预试原样保留，不能与新会话和种子配置混算。`config.draft.json` 是正式实验的配置契约，不是 Pi 自身配置；`ready_to_run=false` 表示正式数学基础、指南、任务与预算尚待冻结。

接入更新：共同模型为 Paratera 的 `DeepSeek-V4.1-Flash`。API 兼容性检查及实际 Pi 流式工具调用均已观测通过，见 [模型接入状态](PROVIDER.md)。正式推理参数、基础接口和预算仍待冻结。开发记录不进入正式准确率。

## 1. 研究问题与两条轨道

主实验是原典形式化建库：双方获得相同的原文命题、原文证明、图形和语言无关的数学验收规格，由 agent 建立定义、选择表示、形式化命题、编写辅助引理和证明。每边保留自己的积累库，使用新的独立任务对话。测量的是固定模型、技能、基础库、验证器共同组成的系统表现；不把结果解释为语言本身的因果优势。

主实验不预先向 agent 提供全部正式定理声明，否则会移除形式化能力这一研究对象。主实验需要预先冻结的是原文完整结论、适用域、允许假设与构造要求。正式输出在实验后逐项核对这些要求。

辅助实验是固定目标证明：事先审核数学等价的 Lean / Litex 定理声明、传递定义和相同前置结果，agent 只补证明与必要局部引理。该实验用于诊断差异来自形式化还是证明；成绩、准备成本和前置库必须与主实验分开，不混用自主积累与人工补齐的依赖。

目前先实现主实验的小规模流程。固定目标诊断不要求先为全书准备 465 对定理，可以选择实际出现差异的代表性子集。

## 2. 公平起点与原文输入

双方固定同一模型精确 ID、provider、可用的推理设置、Pi 提交、预算、机器、源文与输入模式。原文证明向双方可见，因此主实验研究根据原典进行形式化，而非独立发现证明。

原文打包器生成任务内的文本、图形和范围说明。若模型支持图片，双方使用相同渲染页面；若不支持图片，先准备统一审核的图形关系说明和文本。不得给一边图片、给另一边缺失关键图形条件的 OCR。与目标同页的其他条目不自动成为允许的库结果。任务源文、批准文档和当前积累库之外的访问由工具或操作系统限制，不能仅依靠提示词和 `cwd`。

采用等价的现代数学基础，而非一边完整 Mathlib 几何、一边仅四个函数。第一卷从同类实数、序、基础代数和最小二维坐标接口出发；全书分别扩展到比例与同类量、整数与单位、可通约性分类，以及三维几何、面积和体积。基础扩展在对应阶段运行前冻结，准备成本单列，不在正式运行中为单侧临时补库。

当前二维起点已实现为 `real-plane-algebra-v1`：双方共有点类型、点构造、两个坐标访问、从 a 到 b 的向量、点积和行列式共七个名字。原典中的距离、圆、共线、三角形及命题证明由 agent 建立。旧系统的完整种子仅用于开发参考，不加载到任务。每次运行复制并绑定种子哈希，最终文件保留原种子前缀；种子不计作 agent 完成的原文任务。七接口的对应已实测，全部传递数学基础仍需正式审核。

允许各语言生成可由核验器接受的代数自动化证明；不要求战术或命令逐条对应。批准库和传递导入必须审核，不能直接调用待测目标及其等价结论。Lean 的宽泛 tactic 导入也须检查实际导入环境，不能只检查顶层文件名。若现有基础已包含某个测试目标，先改基础边界或显式改分母，不能仍把它作为从零建库的成功项。

解析模型下的源文构造须满足规定对象、非退化与全部构造性质，并记录与原典路线的差别。若另测严格尺规操作序列或仅从特定公理体系推导，应新设轨道，不把解析模型证明混称为这一结果。

## 3. 先完成一个源文验收规格

每项规格包含：源文 ID、变量与域、前提、全部结论、分支、构造见证及性质、允许模型、禁止的弱化、源文定位、审核状态。它是数学要求，不限定 Lean / Litex 的具体语法。

I.1 的草案见 `contracts/EUCLID.I.P001.draft.json`：对任意不同的 A、B，构造 C，使三边等长且 A、B、C 非共线，并符合原文两个规定圆的关系。不能只证明在退化情形中成立，不能把目标改为某个固定三角形，也不要求原文没有给出的唯一性。审阅者还需核对解析模型与原典构造含义，再把草案标为冻结。

首批开发项是 I.1–I.8，包含必需定义和辅助证明。I.2 要关注起点与给定线段端点重合的情形，I.5 要保留底角与底边以下角的两部分，I.7 要保留同侧等适用条件。这些提醒不是完整规格，不能替代逐项读原文。

## 4. 运行系统

数据流：任务清单与规格 → Python 配对调度 → Pi RPC → 当前语言的受控读写与检查工具 → Lean / Litex 适配器 → 独立机器验收 → 候选库 → 实验后语义与假设审核 → 评分。

第一版沿用 Python 编排，通过 Pi RPC 启动真正的 agent 工具循环，替换原来直接调用 `chat.completions.create` 的循环。Pi 的 `prompt` 成功响应只表示接收请求；任务结束以 `agent_settled` 为准。完整记录 `message_end`、工具、压缩、重试、退出事件；stdout 持续读取，stderr 独立保存。无需为了这一步重写 Pi 源码。

每个任务使用新 agent 对话，不继承前项聊天；通过索引读取本语言已提交的库。当前任务内迭代保留原生验证器进程，普通失败保留已接受上下文；硬终止后重新加载批准基础并逐条重放接受日志。Lean 失败不推进 env；Litex 按语句记录接受结果，不能按整批 failure 假设全部回滚。最终文件另开进程检查，不关闭书写会话。v6 已实现跨任务边界发布和失败项回滚。

任务写入暂存区。只有保存文件在新进程中通过当前任务与实际依赖的机器检查，且未改动既有冻结文件、未引入新信任债务，才进入 `machine_checked_candidate` 库；这仍不等于源文语义成功。超时或失败的整个任务增量回滚到边界，记录必要的环境重放成本，不把未验收部分偷偷留给下一项。

为了保持自动建库测量，主运行期间不插入人工改证明、补前提或改技能。最终源文语义审核不把反馈返回同一主运行；审核时间另列。审核定义的实际含义和目标的展开后陈述，不能仅按定理名判断。自动或模型审查可辅助定位，但不能充当未经核对的真值裁判。未完成语义审核时只报告候选通过率，不称为准确率。

若前置结论缺失，可在当前任务预算内实际补证；禁止把它视为公理。仍无法推进则保留为依赖阻塞。任何主运行之后的补证、人工干预与复测进入单独 repair 阶段，不覆盖首次主运行成绩。

## 5. 工具与技能

公共能力限定为：读取批准资料和当前库、编辑当前任务增量、调用当前语言检查器、提交产物。通过受限工具或隔离环境实现路径与命令限制；不把任意 shell 访问当作可靠的读取边界。检查器自身和受保护基础由实验控制器管理。

Litex 采用 `litex-skill` 的 basics、concept-modeler、proof-writer、textbook-translator 主线，按需补充 `litex_skill_geo` 的当前内核契约、几何语义提醒与错误解析。剔除历史命令、未验证案例、测试题正式答案、内核维护技能和信任兜底。Lean 配置等同教学目标的语法、建模、证明、模块与错误诊断指南。技能冻结内容和哈希，不能声称字数相同就等价。

Litex 适配器必须实测当前二进制的 Session、JSON、退出码及 strict 契约；失败后自动转 axiom 的逻辑不迁移。Lean 适配器可复用既有 REPL 协议，但需修正项目路径、确认 REPL 与工具链兼容，并增加最终检查、目标检查与传递假设审计。现有解析代码的成功判断不能直接视为完整实验验收。

Lean 最终检查包括核对实际目标、独立构建与 `#print axioms`，排除 `sorryAx` 和未经批准的新增假设；标准逻辑基础按冻结政策允许。Litex 检查独立模块结果、导入范围以及直接与传递的 trust/axiom。两边均不允许修改核验器或声明待证目标为新公理。所有结论相对于各自公开的核验器与批准基础成立，不把 strict 成功称作无任何数学假设。

## 6. 预算、计时与事件

开发初值是每项 20 分钟、最多 60 次检查调用；单次检查初值 180 秒，实际超时纳入总预算。该预算只用于 pilot 校准，不能在没有真实延迟数据时预测全书时长。定义、辅助条目和共享接口有自己的记录与预算，消耗计入整体建库时间，不作为免费成果。

正式预算在双方共同 pilot 后统一冻结。任务截止时间覆盖 agent 启动、依赖加载、模型等待、所有工具、重试、重放和最终独立验收；最终检查也必须在截止前完成，不能在一侧另加免费检查时间。另设整次运行硬截止；完整预算尚未确定时配置不得进入可运行状态。Token 先测量，若 provider 不能可靠报告，就不声称严格执行累计 token 上限。

使用单调时钟测量本地持续时间，UTC 时间戳记录事件顺序。至少保存 task_id、run_id、语言、模型、源文/规格/基础/技能/产物哈希、开始结束、检查调用、原始反馈、重启重放、最终状态。Pi 的累计流式 usage 不能逐帧相加；从去重的最终消息及实际调用记录核算，压缩调用另记，缺失为 null。保留 provider 的原始字段，不未经核对地把缓存 token 重复加入输入。

记录 `setup_seconds`、`agent_task_seconds`、`model_request_seconds`、`checker_seconds`、`final_integration_seconds`、`semantic_review_seconds`。模型请求时间包括服务排队和网络，不叫纯思考时间。任务总墙钟直接测量；重叠工具时长不能相加当作总墙钟。正式机器输入准备预先固定，人工规格准备与审核成本另外报告。

正式主比较单任务串行，在每个任务对内随机决定语言先后，并交错执行两个各自保留库的语言运行，避免共享 CPU/GPU 争用。记录随机种子、预热和缓存政策。支持的原生增量能力可以使用，依赖冷启动和最终整卷集成另有记录，不能一边每步全库冷编译、一边只报热检查而不披露差别。

关闭 Pi 缓存预热不等于关闭服务端提示缓存。服务端缓存若不可控制，就保留实际 cache-read 计数、交错语言顺序并披露运行时间；总输入 token 和未命中缓存输入分别报告。不能只报告未缓存输入，把缓存部分当作没有发生的上下文，也不能把一次先后顺序造成的时延差异解释成语言优势。

基础设施故障保留原失败和重试。主指标包含真实端到端成本，并额外报告基础设施故障比例；仅在预先规定的独立诊断中排除外部故障，不能事后删除慢例或重跑到成功。

## 7. 评分

主要指标是完整正确建库率：源文语义完整、独立机器验收通过、假设符合政策的编号命题数，除以预先登记的编号命题总数。第一卷正式切片的分母为 48，全书为 465；只跑了第一卷时不能把剩余卷称作已经测试失败。定义和辅助条目另计。已登记运行内超时、依赖阻塞、预算结束未尝试的目标留在分母，并分别报告原因。

同时报告形式化正确率、机器候选通过率、完整正确率，避免把“编译通过”称作“准确”。主运行全部产物冻结后审核目标及其定义语义；最终正确结果还需在实际集成环境中成立，不能只依据保留了隐含上下文的交互 Session。

时间主指标为相同预算下完成的正确命题数，以及按正确产物首次完成时间重建的覆盖曲线。失败不会因为耗时短而算作更快成功。双方共同正确的子集才计算配对耗时比，并明确该子集大小及选择偏差。另报双方完成到同一覆盖数量的时间；达不到该覆盖的一方记未达到。

推荐先进行第一卷一次正式配对运行，再决定资源是否支持三次独立重复。重复运行从初始基础重建，不继承此前答案或调参反馈。顺序建库的命题存在依赖，一整次建库运行才是重复实验单位；不能将 465 项当作独立样本制造显著性。小重复数只给描述性结果，固定目标诊断可以采用独立题目的配对统计，须另行报告。

I.1–I.8 用于开发，最终报告明确其调参身份，并单列 I.9–I.48 的结果。不得宣称这些源文从未出现在模型训练数据中；这里只控制本次运行可读取的正式答案。

## 8. 实施顺序与交付门槛

第一步：工程 smoke。连接 Pi，跑固定小型正例、错误目标负例、普通失败后保留上下文、硬错误后重放，以及已保存文件的独立检查。确认模型能实际发起工具调用、失败不会被判成功、事件能完整计时。此步骤不生成正式准确率。

第二步：I.1 完整闭环。审核首项规格和最小数学基础；双方各自从原文写出正式定义及定理、证明、独立验收和事件记录，再核对数学语义。必须能够给出完整原文构造，而不是只生成可编译的文件。

第三步：I.1–I.8 开发 pilot。完成所需定义、调试错误反馈与日志、测量主要耗时、冻结共同预算和技能。该阶段不作最终胜负结论。

第四步：第一卷 48 项正式配对运行。冻结起点后从头运行，输出机器原始记录、语义审核结果、分卷正确率、正确覆盖随时间曲线、共同成功题耗时及定义/辅助成本。先一对，再决定重复次数。

第五步：按依赖扩展到全书。平面几何 I–IV；完整比例 V 和 VI；整数 VII–IX；无理量 X；三维及穷竭 XI–XIII。这是工程里程碑，不替代审核过的逻辑依赖图。每次新增领域先完成两侧基础对齐，再冻结对应阶段；不在运行途中修内核后把不同版本合并报告。

后续完整工程需要覆盖 Pi RPC、配对调度、源文打包、两种适配器、工作区限制、语义裁判与计分；可在现有开发实现上拆分和扩展，不要求为了目录命名重写已经验证的部分。

当前实际实现位于 `runtime/run.py`（Pi RPC 与计量）、`runtime/prepare.py`（源文打包与 job）、`runtime/tool_host.py`（持续工具服务、边界与凭据）、`runtime/native_sessions.py`（原生 Session/REPL 与重放日志）、`runtime/verifier_feedback.py`（原生语言反馈）、`runtime/tools.ts`（七工具和原始 usage）。离线控制还覆盖真实 Pi 扩展连接，且禁止模型调用。`audit_candidate.py` 可做事后机器与公理依赖复核，v6 已在 submit 中实现预算内声明/公理 gate。跨任务发布、整项回滚、恢复和统计位于 runtime/batch.py 与 batch_report.py；语义审核由人工证书导入，全面基础等价性认证仍待完成。
