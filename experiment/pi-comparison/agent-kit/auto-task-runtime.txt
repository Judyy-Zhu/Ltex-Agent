Use the whole-task candidate protocol. Each original definition/proposition has at most five candidate rounds TOTAL, including the first attempt. One round is generating a complete definition/proof increment, submitting it to the native kernel and receiving feedback; a network/API failure also consumes a round. A repair or retry uses the same shared allowance. Helper declarations share the task counter; they do not get separate allowances. No task, batch or checker time limit applies. Time and tokens are measured outcomes.

Keep explanations concise. Write the complete candidate to candidate.lean or candidate.lit and call check(incremental). Include necessary helpers in that same candidate, without repeating the frozen seed or predecessor library. Source writes need no manual item ID: the controller uses this task's primary ID. Read the actual native diagnostics and replace the complete candidate at the same path after failure. Do not spend candidate rounds on separate syntax probes or helper-only files. A generation that ends without submitting code also consumes one round. Five failures consisting only of network/API errors checkpoint this SAME task, without counting a mathematical failure; explicit restart opens a fresh window while retaining all history. A partially used window keeps its remaining attempts. Other exhausted windows finish under the ordinary failure policy.

Definition tasks require the actual definitions, domains and a clear representation of the source concepts. Prove only facts explicitly asserted by the source or needed for well-definedness; do not invent an additional project of semantic-bridge theorems. Proposition tasks require complete statements and checked proofs. Existing approved definitions and own-language published results may be reused. Do not assume a failed predecessor or add unchecked axioms.

After a COMPLETE candidate passes, the controller generates a public index from native declaration metadata, assembles the saved final file, runs independent final verification, checks declaration/axiom dependencies and saves the submission. You do not write interfaces.json, clause labels, final files or submit metadata. check returns task_completed=true only when those machine gates pass. Do not make more tool or model calls after task_completed=true. If auto_finalization.completed=false, read its final_check and gate diagnostics and repair the same complete candidate; administrative steps do not consume additional candidate rounds. Semantic review remains an optional pending annotation and does not block passing. Controller-generated source associations are unreviewed task-level associations, not a semantic assessment.

The current task, its complete primary TXT, foundation, seed, diagnostic field guide and own-language library index are supplied up front. Do not repeatedly retrieve identical reference material. Additional context TXT and published source increments are available through read_input/read_library as needed. The verifier always includes the immutable seed and complete published own-language predecessor library.

The controller persists the Pi conversation, files, receipts, used attempts and native journal. After recovery, read remaining_budget and the saved receipts before acting. Never reset attempt IDs, reconstruct completed tasks or recheck an unchanged accepted candidate merely because the process restarted. A transport error followed by an accepted final submission is still a successful task. Finalization runs locally without another API request. Interrupted finalization is recovered locally on restart with no new candidate round.
