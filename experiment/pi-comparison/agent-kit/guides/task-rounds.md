# Five total task attempts and checkpoint recovery

Each original source task has five TOTAL attempts in its current execution window, first attempt included. One full definition/proof candidate submitted to the native kernel uses an attempt. A network/API failure also uses an attempt. These are one shared allowance, not five attempts per helper or five extra network retries. A generation ending without submitted code, including output truncation, also uses an attempt. There is no task, batch or verifier time limit. Actual time, tokens and waiting are measured.

Read the task, source TXT, seed and own-language predecessor library. Save the COMPLETE new task increment in candidate.lean or candidate.lit with base="none". Include necessary auxiliary definitions and proofs in this same file; do not repeat the already loaded seed/predecessor library. The controller automatically supplies the primary item ID if metadata is omitted. Call check(incremental), read the complete native feedback, repair the complete candidate at the SAME path and check again. Helper names and alternate file names do not reset the shared allowance.

An early network/API failure does not force the task to fail. A later successful candidate and complete final/submission gates count as passed normally. If all five attempts fail only because of network/API problems, the controller stops and checkpoints this task without marking a mathematical failure or advancing to the next task. An explicit restart resumes this same source task and opens a fresh five-attempt window; the previous five attempts, source files, conversation, time and token records remain in history. A manually interrupted partial window keeps its remaining allowance. A window exhausted with actual proof/generation failures is terminal under the ordinary task policy.

Both workers use the same recovery policy. Complete tasks are never regenerated. Unfinished work restores its own Pi conversation, current files, receipts, item registry and native verifier journal. If native verification itself was interrupted, the controller restores its reserved attempt and receipt rather than debiting another attempt. Saved tool-operation results can be returned without repeating their side effects. A lost in-flight API request may need to be sent again, and missing usage remains unknown.

A failed candidate may leave a valid prefix in the session. That prefix alone is not task success: the COMPLETE current candidate must pass. Once it passes, save interfaces.json, assemble a separate final module with base="accepted" and empty content, call check(final), then submit. Final verification and publication do not consume candidate attempts and cannot add unchecked mathematical code. Connection failures during finalization are retried at most five consecutive times and checkpoint the already accepted candidate if still unsuccessful.

remaining_budget.task_rounds and check.task_rounds expose limit, used, remaining, total_used, exhausted, transport_only_exhausted, current-window rounds and full history. kind is candidate, generation or transport; api_attempt_id links connection failures to provider logs. null for a time/check-count limit means unlimited. Reports distinguish attempt_window_used (at most five) from task_attempt_count and task_retry_count over the entire task history, which includes earlier API-only windows. Native item-check counts remain separate. Time/tokens include every execution segment and waiting; a manual stop excludes the time when the experiment was not running. Optional semantic review never blocks passing, publication or primary scoring.
