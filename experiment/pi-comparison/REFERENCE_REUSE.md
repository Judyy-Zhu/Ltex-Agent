# 旧几何建库系统在新实验中的复用

旧项目可作为语言经验、初始接口与验证器的来源；它们的自定义几何任务不替代《几何原本》的源文任务。这里是实验准备记录，不挂载给正式求解 agent，避免将旧目标、答案及历史成功标签混入输入。

## 已实际对照的内容

两边各有 39 个定义任务和 165 个定理任务。通过 AST 只读取任务数据，未导入执行 API 代码：两套定义任务 ID 顺序相同，36 个描述完全一致，前三个只在坐标写法 `p(1)` / `p.1` 等处不同；两套 165 个定理任务的 ID 顺序、description、task_type、hints 完全一致。

这证明任务文本高度对齐，不证明两种语言的生成产物等价，更不证明这些自定义任务与原典 465 个命题一一对应。旧任务可用于工程回归或独立的历史复现实验；与新正式目标或其关键辅助证明重叠的完整解答不进入新指南。

定义种子中，Litex 的 `points/vec/dot/det` 与 Lean 的 `Point/vec/dot/det` 是同一坐标数学意图，适合作为新基础候选。它们尚不能覆盖构造题所需的全部开方、存在性等支持能力。完整 theorem seed 已提供距离、直线、圆、全等、相似等定义；整份加载会改变“由 agent 建立这些概念”的任务边界，不能当作最小初始基础直接采用。

## 指南保留与改写

旧 Litex 指南 806 行，旧 Lean 指南 514 行，均已全文检查。可保留的经验是类型和坐标、函数与谓词区分、量词、展开、存在见证、首错调试，以及两种语言各自合适的证明风格。

以下部分不能原样迁移：

- Lean §12.4 和 Litex §9.4 都建议卡住时使用未证明占位。这与新实验主成绩的无新增证明债务规则冲突；正式输入移除，而不是仅在末尾加一条禁令。
- Litex §4 强调自定义谓词 `$` 前缀，而 §4.1 的一些“正确”代码又没有该前缀；对前提重复陈述的说明也不一致。新核心例子以本机实际核验结果为准，复杂条件语法逐条补探针。
- Litex §9.4 仍描述 `try` 与自动公理兜底，而旧验证器实际 `validate` 路径直接提交代码；不能从这段说明推断当前事务语义。
- 旧指南允许为了好证明而更换定义、增加非零前提。新指南只允许保持源文语义的表示调整，所需非零性应从原前提推出；不能静默改强前提或削弱结论。
- 两边“共线＋等距的中点”与“坐标平均的中点”并非无条件等价：当两端重合时，前一表示可接受不在该点的任意点，后一表示不接受。新实验须明确退化域并证明桥接，不能只选较好证明的形式。
- Lean 的“禁止 import”是旧 REPL 增量提交约束，不是独立 `.lean` 模块的一般规则。当前本机检查还提示旧 `Mathlib.Data.Real.Basic` 已弃用，改用 `Mathlib.Basic.Real.Basic`；旧文件不直接修改，新教学例子使用当前版本写法。
- 旧指南中完整的几何定义与定理证明按具体目标审查，不整份注入。新核心教材改用函数、谓词、见证和元组的小例子，避免将待测原典的正式答案当教学。

新指南见 `agent-kit/guides/lean-core.md`、`litex-core.md` 与共同 `curriculum.json`。先加载核心和专题目录，专题按需读取。匹配功能覆盖、材料访问与验收规则，不要求字数相等；允许各自使用自然的证明机制。需要 U09 开方与定义域等专题经过验证，才可认为 I.1 的语言准备充分。

## 验证器和提示词复用

保留会话增量、代码提取、超时、错误反馈、已接受代码导出，以及种子和 agent 新增库分开的组织方式。将旧的“每轮完整指南＋完整积累库＋只输出代码”改为 Pi 的工具循环和按需接口读取；共同任务、语言说明和检查工具分离。

Lean 旧适配器具有 REPL `env` 前进及重放机制，但会在 REPL 不可用时回退整文件模式，且以无 error 消息或进程成功为通过条件。新工具必须公开实际模式，复验重放完整性，并增加保存模块检查、目标声明存在性、占位与传递假设审计。注释或空增量可在交互层无操作，但不算完成一个新的命题。

Litex 旧适配器维护 `committed`，但 `_ensure_session` 的重启路径只重新载入 seed，没有重放该列表；新工具不能原样依赖它恢复整个积累库。旧实现还含 axiom fallback 与未使用的 try 辅助代码，新适配器不暴露这些能力。必须按当前二进制实测结果管理逐语句提交、已接受前缀与 JSON 流。

两边旧 theorem 入口的种子选择也不完全相同：Litex 固定使用其 theorem seed；Lean 优先选择旧 `LeanGeo/library_final.lean`，缺失时才回退 database seed。新实验一律显式绑定带哈希的批准基础，禁止根据机器上偶然存在的历史文件自动换库。

`TaskAttempt` 的 token 字段和日志结构可参考，但重新用外部单调时钟覆盖检查、恢复和最终验收。原脚本单次 elapsed 在编译前取值。自动成功计数、按固定 ID 跳过种子定义，以及事后仅按字符串数 sorry/axiom，都不能直接作为新主成绩。

## 工具设计

共同工具使用同一名字和参数结构：`read_input`、`read_docs`、`read_library`、`write_source`、`check`、`remaining_budget`、`submit`。`check` 内部分别调用 Lean REPL / Litex Session，最终模式另起进程验证实际提交范围。

检查反馈统一为 passed、阶段、位置、未解决义务、原生错误摘要、上下文版本、receipt_id；保留原始诊断且两边可以按相同规则读取。不能一边只给一个被裁掉上下文的错误、另一边附加详细解题建议。函数名、native proof automation 和错误用词可以不同。

适配器必须把工作文件和会话状态绑定。追加新内容可复用上下文；修改已接受内容后重同步并重放。多语句批次失败可能已经提交前面的语句，不能假设整批回滚。超时后状态不明则终止该会话并恢复到有证据的前缀。全部实际成本纳入计时。

验收要求两边都具备声明、引用、增量检查、错误恢复、独立保存文件验证和假设审计能力，不要求检查器执行同一算法或相同数量的证明步骤。只有注册并实测这些接口后，才能把它们作为 Pi 工具交给 agent；目前 `tool-contract.json` 仍是接口设计。

## 准备检查

本机观测 Lean 4.35.0 和 Litex 1.1.2-beta。`agent-kit/guides/smoke_guides.py` 检查一组数学意图相同的微型教学代码、错误算式拒绝、Lean sorry 的额外审计需求及 Litex strict axiom 拒绝。具体结果见该目录的 `smoke-receipt.json`；它不是 Pi 运行结果，也不是整卷准确率。

接下来先补齐 I.1 所需的守卫、开方与存在见证专题，审核最小基础；然后注册共同工具并用正反例检查增量恢复、保存文件与 Session 不一致、占位证明和未批准依赖。旧 39/165 项保留为另一组任务来源，正式原典仍按自身的源文 ID、完整结论和分母计分。

## 后续核对的反馈与预检脚本

已完整读取旧 `scripts/litex_llm_formatter.py`：它保留 run_result、statement_results、errors，包含成功条目的 proof_method/stores/infers。新 v3 final 展示与其函数在真实成功、失败返回上逐字核对；v4 Session 还完整保留每轮控制字段，不能依赖旧 formatter 关于 session_terminated 总为 false 的注释。

已完整读取旧 `scripts/final_verification.py`：实际内容是 Python/OpenAI 库、二进制、seed、脚本存在性、导入和 Session 启动预检。它不是数学命题的最终验收器；其中旧 39/165 任务和直接 API 环境要求不迁入新实验。新工具分别验证原生会话恢复、独立最终文件和事后假设依赖。

实际固定二进制的 Session 探针确认：一次解析错误后仍能接收下一条输入，不能按 phase=parse 一概重启。普通失败之后的退出汇总还会包含历史拒绝，不能把它当作最后一条候选的响应。原始证据在 `session-reference-probe.json` 与 `session-parse-probe.json`。
